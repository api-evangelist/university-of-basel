# University of Basel

> The University of Basel (Universität Basel), founded 1460, is the oldest university in
> Switzerland. It has no single central developer portal; its machine-readable API surface is
> scholarly infrastructure, spread across four services: the edoc open-access institutional
> repository (DSpace-CRIS), the edoc OAI-PMH metadata interface, the swisscovery/SLSP library
> discovery catalogue (SRU), and DSP-API — the RDF humanities research-data platform built and
> operated by DaSCH, the Swiss National Data and Service Center for the Humanities, which is hosted
> at the University of Basel.

Generated by API Evangelist on 2026-08-27 from the University of Basel apis.yml index and the
artifacts in this repository. Not published by the University of Basel. Every URL below was
fetched and its status recorded on that date.

## What you can call without a key

- 54 DSP-API GET operations are marked "Publicly accessible" in the contract — project listing,
  full-text search, Gravsearch graph queries, ontology reads, IIIF manifests, TEI rendering,
  resource history, /health and /version.
- The edoc DSpace REST API, the edoc OAI-PMH interface, and the swisscovery SRU interface are all
  anonymous for reads.
- There is no pricing, no plan and no quota on any API call. See plans/.

## APIs

- [DaSCH DSP-API](https://api.dasch.swiss): RDF-based HTTP API for long-term preservation,
  querying, annotation and linking of humanities research data. OpenAPI 3.1, 145 paths /
  180 operations, v37.8.0. Contract: https://api.dasch.swiss/api/docs/docs.yaml
- [edoc DSpace REST API](https://edoc.unibas.ch/server/api): HAL+JSON REST API of edoc, the
  open-access institutional repository. DSpace 7.6.2 / DSpace-CRIS cris-2023.02.06.
- [edoc OAI-PMH](https://edoc.unibas.ch/server/oai/request): OAI-PMH 2.0 harvesting. Eleven
  metadata prefixes (oai_dc, qdc, dim, mods, mets, marc, rdf, ore, didl, etdms, uketd_dc) plus an
  OpenAIRE-CRIS 1.1 stream at /server/oai/openairecris.
- [swisscovery SRU](https://swisscovery.slsp.ch/view/sru/41SLSP_UBS): SRU 1.2 search/retrieve over
  the SLSP Alma catalogue for the Basel institution zone (41SLSP_UBS).

## Authentication

- DSP-API: obtain a JWT with `POST /v2/authentication` carrying
  `{"identifier_type": "...", "password": "..."}`, then send `Authorization: Bearer <token>`.
  `DELETE /v2/authentication` invalidates it server-side. HTTP Basic is declared in the contract but
  the docs call every method other than bearer deprecated.
- There is no OAuth 2.0, no OpenID Connect and no API key anywhere in this estate. No
  `/.well-known/openid-configuration` or `/.well-known/oauth-authorization-server` is served on any
  host (all 404, probed 2026-08-27).
- Authorization is enforced by the DSP permissions system (administrative permissions and default
  object access permissions bound to a group within a project), not by token scope.

## Before you write

- Read the project ontology first. There is no global content schema: a DSP resource's valid shape
  is whatever the project's ontology declares. Fetch it with
  `GET /v2/ontologies/allentities/{ontologyIri}`.
- Every mutation carries `knora-api:lastModificationDate`. If someone else wrote since you read,
  the request fails 409. This is the only double-write guard — there is no Idempotency-Key.
- Rehearse deletes. `GET /v2/resources/candelete`, `/v2/ontologies/candeleteclass/{iri}`,
  `/v2/ontologies/candeleteproperty/{iri}`, `/v2/ontologies/candeleteontology/{iri}`,
  `POST /v2/ontologies/candeletecardinalities` and `GET /admin/lists/candelete/{iri}` all answer
  whether a destructive change is permissible without performing it.
- Ordinary deletes are SOFT. `POST /v2/resources/delete` and `POST /v2/values/delete` mark the
  object deleted and retain it; the IRI and ARK permalink still resolve, returning a
  `knora-base:DeletedResource` with its deleteDate and deleteComment. But no un-delete route is
  published for resources or values.
- `erase` is NOT delete. `POST /v2/resources/erase`, `POST /v2/values/erase`,
  `POST /v2/values/erasehistory` and
  `DELETE /admin/projects/shortcode/{shortcode}/erase` permanently and irrecoverably remove data.
  The contract says so in capitals. Never call these without a human.
- Users and groups ARE restorable: delete sets `status: false`, and setting it back to `true`
  un-deletes. That is the only documented reversal operation in the estate.

## Errors

- No RFC 9457. DSP-API v2 and the Admin API return `{"message": "..."}` with no machine-readable
  code; only API v3 adds `errors[].code` from a closed enum (`resource_not_found`,
  `project_not_found`, `ontology_not_found`, `export_in_progress`, …).
- 400 validation / ontology constraint, 401 bad credentials, 403 permissions, 404 not found (or
  soft-deleted), 409 edit conflict, 500 server, 503 search timeout.

## Rate limits

None published, and none signalled. No `RateLimit-*`, no `X-RateLimit-*`, no `Retry-After` on any
live response from any host; no 429 declared on any operation. Harvest OAI-PMH and SRU politely and
serially — the courtesy is yours to supply.

## SDKs and tooling

- [dsp-tools](https://pypi.org/project/dsp-tools/) — Python CLI and library, v19.0.2.post0

  upload, ingest, migration, and a full local DSP stack in Docker.

  v12.0.1 (2026-06-15).
- [@dasch-swiss/dsp-ui](https://www.npmjs.com/package/@dasch-swiss/dsp-ui) — Angular UI library,
  v1.8.0 (2021-08-13). Dormant; five years behind the API it wraps.

## Testing

There is no hosted sandbox. `dsp-tools start-stack` runs DSP-API, DSP-APP, Sipi and Fuseki locally
in Docker; the published local system-administrator login is `root@example.com` / `test`, which is
valid on the local stack only.

## Known gaps

- No `/.well-known/` document of any kind on any host (security.txt, api-catalog,
  openid-configuration, oauth-authorization-server, agent-card.json — all 404 or 503).
- No A2A agent card and no MCP server. The only MCP declaration in the DSP-API repository is a
  `metals` stdio server for contributors' coding agents, not an API surface.
- No published rate limits, no idempotency keys, no RFC 9457 problem details, no Sunset/Deprecation
  headers, no request-id header.
- No published deprecation policy or SLA.
